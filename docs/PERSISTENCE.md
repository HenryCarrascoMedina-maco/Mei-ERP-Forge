# Persistence Guide — EF Core

> Status: introduced in **v1.0.0-rc.1**. The platform uses **EF Core** as the default persistence
> layer, isolated in the `ErpPlatform.Persistence` package. `ErpPlatform.CrossCutting` stays
> persistence-agnostic. The default provider is **SQLite** (zero-config, file-based) so a fresh clone
> runs with a real, persistent database out of the box.

## 1. How it fits together

```
ErpPlatform.CrossCutting   (persistence-agnostic: entities, responses, pagination, auth)
        ▲
ErpPlatform.Persistence    (EF Core: ErpDbContext, EfRepository<T>, auditing, async pagination, seeding)
        ▲
ErpBackend.Api
   ├─ Persistence/AppDbContext.cs         : ErpDbContext (ApplyConfigurationsFromAssembly)
   ├─ Persistence/AppDbContextFactory.cs  : design-time factory for `dotnet ef`
   ├─ Migrations/                          : provider-specific migrations
   └─ Modules/<Name>/                       : generated by erpgen
        ├─ <Name>Configuration.Generated.cs : IEntityTypeConfiguration<<Name>>
        └─ <Name>EfRepository.Generated.cs   : EfRepository<<Name>>, I<Name>Repository
```

Generated modules require **no** changes to `AppDbContext`: each ships an
`IEntityTypeConfiguration<T>` that `ApplyConfigurationsFromAssembly` discovers automatically.

## 2. Configuration

Bound from the `Database` section + the `Default` connection string. Everything is environment-overridable.

```jsonc
// appsettings.json
"Database": {
  "Provider": "Sqlite",        // Sqlite (default) | SqlServer | PostgreSql
  "MigrateOnStartup": true     // apply pending migrations on boot (great for demo/containers)
},
"ConnectionStrings": {
  "Default": "Data Source=erp-platform.db"
}
```

| Key | Meaning | Default |
|-----|---------|---------|
| `Database:Provider` | Relational provider | `Sqlite` |
| `Database:ConnectionString` | Explicit connection (overrides `ConnectionStrings:Default`) | — |
| `Database:MigrateOnStartup` | Apply migrations at startup | `false` (the API sample sets `true`) |
| `ConnectionStrings:Default` | Connection string | SQLite file fallback |

**Environment overrides** (no code/file change — ideal for containers/CI):
```
Database__Provider=SqlServer
ConnectionStrings__Default=Server=...;Database=...;User Id=...;Password=...
```

### Startup wiring
```csharp
builder.Services.AddErpPersistence<AppDbContext>(builder.Configuration);
// ...
var app = builder.Build();
await app.Services.InitializeErpDatabaseAsync<AppDbContext>(); // migrate (if enabled) + run seeders
```

## 3. SQLite (default)

No setup required — a local `*.db` file is created on first run (and auto-migrated when
`MigrateOnStartup` is true). The file is **gitignored** (`*.db`, `*.db-shm`, `*.db-wal`). This is the
provider used for the public demo: zero configuration, real persistence, survives restarts.

## 4. Using `dotnet ef`

The API references `Microsoft.EntityFrameworkCore.Design`; install the CLI once:
```bash
dotnet tool install --global dotnet-ef --version 10.0.8
```
A design-time `AppDbContextFactory` lets the EF tools build the context **without** running the app
(reads `appsettings*.json`, uses SQLite). Common commands (run from `ErpBackend.Api`):
```bash
dotnet ef migrations add <Name>      # after generating/changing a module
dotnet ef database update            # apply migrations
dotnet ef migrations remove          # undo the last (unapplied) migration
```

### Typical flow when adding a module
```bash
erpgen module --manifest Invoice.module.json --project ./ErpBackend.Api --namespace ErpBackend.Api
dotnet ef migrations add AddInvoice
dotnet ef database update            # or just run the app with MigrateOnStartup=true
```

## 5. Migrations are provider-specific

A migration generated for SQLite is **not** portable to SQL Server/PostgreSQL (column types,
defaults and SQL differ). For multiple providers, keep a **separate migrations set per provider**,
e.g. by output directory and a `--` provider switch:
```bash
dotnet ef migrations add Init --output-dir Migrations/Sqlite     -- --provider Sqlite
dotnet ef migrations add Init --output-dir Migrations/SqlServer  -- --provider SqlServer
```
(Reading the provider arg in `AppDbContextFactory` to pick `UseSqlite`/`UseSqlServer`.) The RC ships
the **SQLite** migration only; additional provider migrations are added when a customer needs them.

## 6. SQL Server / PostgreSQL

The `ErpPlatform.Persistence` package references **only** the SQLite provider to keep the default
install light. To use another provider, reference its package and pass a `configure` delegate:

```csharp
// SQL Server — after: dotnet add package Microsoft.EntityFrameworkCore.SqlServer
builder.Services.AddErpPersistence<AppDbContext>(
    builder.Configuration,
    opt => opt.UseSqlServer(builder.Configuration.GetConnectionString("Default")));

// PostgreSQL — after: dotnet add package Npgsql.EntityFrameworkCore.PostgreSQL
builder.Services.AddErpPersistence<AppDbContext>(
    builder.Configuration,
    opt => opt.UseNpgsql(builder.Configuration.GetConnectionString("Default")));
```
Without a delegate, `Provider` is read from config; `SqlServer`/`PostgreSql` throw a clear message
guiding you to the delegate (or a future `ErpPlatform.Persistence.*` companion package).

All entity mapping avoids provider-specific types (GUID keys, `HasMaxLength`, `decimal(18,2)` via a
global convention, primitive-collection JSON for `multiselect`), so the model is portable; only the
**migrations** are per-provider.

## 7. Auditing & soft-delete (automatic)

`ErpDbContext` + the audit interceptor handle these transparently on every `SaveChanges`:
- `CreatedAt`/`CreatedBy` on insert, `UpdatedAt`/`UpdatedBy` on update (user from `ICurrentUserService`).
- Entities deriving from `SoftDeleteEntity` are **logically** deleted (`IsDeleted`/`DeletedAt`/`DeletedBy`)
  and hidden by a global query filter; `AuditableEntity`/`BaseEntity` entities are physically removed.

## 8. Docker readiness (design)

No Docker files ship yet, but persistence is container-ready:
- Provider and connection come from env vars (`Database__Provider`, `ConnectionStrings__Default`).
- `MigrateOnStartup=true` + `InitializeErpDatabaseAsync` means `docker compose up` applies migrations
  automatically on first boot.
- The SQLite file path is configurable, so it can live on a mounted volume (or switch to a
  server-based provider for production).

## 9. Search strategy (current vs future)

Generated list endpoints use `(e.Field ?? "").ToLower().Contains(term)` — translatable by EF Core
**and** valid on the in-memory store. It is intentionally simple (no index/collation tuning).
**Future improvements** (not in the RC): a provider-optimized strategy (`EF.Functions.Like`,
PostgreSQL `ILIKE`, SQL Server full-text) or a pluggable search abstraction.
